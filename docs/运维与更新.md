# 运维与更新

本文说明 cfquant 的本地服务启停、日志清理、版本检查和更新策略。

## Level2 适配升级

本次 Level2 升级需要同时更新 SDK、Web 和 QMT 桥代码，包括新增 `cfquant/level2.py`；极致模式需同步所用自包含 LITE 入口。更新后重启 Web，并完整退出重启 QMT 和使用 SDK 的 Python 进程，避免旧模块仍驻留内存。不要仅刷新网页或只重启策略。

功能、模式范围、千档限制及只读验收步骤见 [Level2 行情适配说明](Level2行情适配说明.md)。无需为普通 Level2 配置额外的千档接口；没有权限或行情时不能把空数据判为通过。

## 启停脚本

项目根目录提供以下脚本：

```text
start_cfquant.bat       启动本地服务
stop_cfquant.bat        停止本地服务
restart_cfquant.bat     重启本地服务
```

通常日常运维只需要使用 `restart_cfquant.bat`。重启只会重启 Web 和 PipeHub，并保留 LTtx，避免外部 `cfquant` Python 库的自动发现和通信入口中断。

如果用户双击启动脚本后窗口闪退或网页打不开，优先查看：

```text
log/startup/cfquant_startup.log
log/web/cfquant_web_server.*.stderr.log
```

新版 `start_cfquant.bat` 会在启动后等待 Web 健康接口真正可用。若目标端口已经是 cfquant Web，会直接复用已有实例并打开页面；若端口被其他程序占用，会提示占用进程并要求停止该进程或改用 `CFQUANT_WEB_PORT`。启动失败时窗口会停留，并输出最近的启动日志和错误日志，不再直接闪退。

`start_cfquant.bat`、`restart_cfquant.bat` 和 `stop_cfquant.bat` 是项目保留的英文入口。重启会保留 LTtx，只等待旧 Web 端口释放后再启动；停止表示完整退出，会停止 Web、PipeHub 和 LTtx。停止失败时会保留窗口，方便查看失败原因。

需要把错误完整留在当前窗口时，可以在命令行中运行：

```bat
start_cfquant.bat --foreground
```

或：

```bat
start_cfquant.bat --debug
```

自动化脚本中如果不希望失败时停在 `pause`，可以设置：

```bat
set CFQUANT_START_NO_PAUSE=1
```

也可以分别设置 `CFQUANT_RESTART_NO_PAUSE=1` 或 `CFQUANT_STOP_NO_PAUSE=1` 控制重启、停止脚本。

## 修改 LITE 桥脚本并让其生效

LITE 模式（`mode=lite`）下，QMT 实际运行的不是项目里的 `qmt_scripts/CFQUANT_LITE.py`，而是部署到 QMT 目录的托管策略包。因此**直接改源文件不会生效**，必须走部署流程。

### 生效链路

```text
改 qmt_scripts/CFQUANT_LITE.py
  → POST /api/account-config/update-core   部署（把源文件打包成托管策略 .rzrk 并写入 QMT 目录）
  → POST /api/qmt/processes/stop           停止 QMT
  → POST /api/qmt/processes/start          启动 QMT（策略启动时加载新包）
```

**三个必须遵守的约束**（都踩过坑）：

1. **`update-core` 要求 QMT 已停止**，否则返回 `409 qmt_running`。
2. **不要用 `cp` 直接覆盖 QMT 目录下的脚本文件**。部署流程会往脚本里注入
   `EMBEDDED_RUNTIME_CONFIG`（账号/桥接/通道等身份信息），直接复制会把这段注入内容清空，
   导致策略启动后卡在 `awaiting account mode confirmation from cfquant Web`，所有交易请求被拒。
3. **入口脚本名是 `CFQ_<账号>_LITE.py`**（如 `CFQ_10110148_LITE.py`），不是 `CFQUANT_LITE.py`。
   前者是 QMT 侧实际导入的托管策略，后者只是项目的源文件模板。

### 部署与重启示例

以账号 `10110148`、`qmt_dir=D:\东北证券NET专业版(测试版)\bin.x64` 为例：

```bash
# 1) 停止 QMT
python -c "
import json,urllib.request
body=json.dumps({'targets':[{'qmt_dir':'D:/东北证券NET专业版(测试版)/bin.x64'}]}).encode()
req=urllib.request.Request('http://127.0.0.1:8765/api/qmt/processes/stop',
    data=body,headers={'Content-Type':'application/json'},method='POST')
print(json.loads(urllib.request.urlopen(req,timeout=60).read())['ok'])
"
sleep 8

# 2) 部署核心与入口策略
python -c "
import json,urllib.request
body={'account_id':'10110148','account_type':'STOCK','bridge_id':'default',
      'qmt_dir':'D:/东北证券NET专业版(测试版)/bin.x64'}
req=urllib.request.Request('http://127.0.0.1:8765/api/account-config/update-core',
    data=json.dumps(body).encode(),headers={'Content-Type':'application/json'},method='POST')
r=json.loads(urllib.request.urlopen(req,timeout=180).read())
print('deploy:',r['ok'],r['data']['qmt_core_deploy']['summary'])
"

# 3) 启动 QMT
python -c "
import json,urllib.request
body=json.dumps({'targets':[{'qmt_dir':'D:/东北证券NET专业版(测试版)/bin.x64'}]}).encode()
req=urllib.request.Request('http://127.0.0.1:8765/api/qmt/processes/start',
    data=body,headers={'Content-Type':'application/json'},method='POST')
print(json.loads(urllib.request.urlopen(req,timeout=60).read())['ok'])
"
```

注意 URL 里的中文路径要写成 `D:/东北证券NET专业版(测试版)/...`（正斜杠）；写成反斜杠会被
JSON 转义破坏，返回 `invalid json: 'utf-8' codec can't decode ...`。

### 等待就绪

QMT 启动后策略需要时间加载，且刚启动的一两分钟内可能返回
`lite/trade: Managed strategy is awaiting account mode confirmation`（握手进行中），
属正常现象，稍后自行恢复；持续超过 2 分钟未恢复才需要排查。
用下面的循环确认就绪：

```bash
for i in $(seq 1 10); do
  sleep 25
  R=$(python -u -c "
import cfquant
cfquant.configure(transport='auto',bridge_id='default',timeout=15.0)
from cfquant.xttrader import XtQuantTrader, close_trade_client
from cfquant.xttype import StockAccount
acct=StockAccount('10110148','STOCK','default')
t=XtQuantTrader(callback=None,account=acct)
print('OK' if t.connect()==0 else 'FAIL')
t.disconnect(); close_trade_client()
" 2>&1 | grep -E "^OK|^FAIL")
  echo "try$i: $R"
  [[ "$R" == OK ]] && break
done
```

### 验证部署确实生效

不要只看部署接口返回的 `ok`，要确认 QMT 侧加载了新版。两种方式：

- **行为验证**：调用一个只有新版才有的行为（例如新增的日志行、新的接口参数），
  观察 QMT 日志是否出现。QMT 侧日志在
  `D:\东北证券NET专业版(测试版)\userdata\log\XtClient_FormulaOutput_*.log`，
  **GBK 编码**，且日志文本已被翻译成中文（如 `普通桥响应完成`、`总耗时=`）。
- **包内容验证**：解密托管策略包确认源码，见下节。

### 确认托管策略包内容（排查用）

部署后的策略是 AES-CFB 加密的 `.rzrk` 包，可用项目自带工具解密核对：

```python
import sys, json
sys.path.insert(0, '.')
from cfquant.qmt_strategy_package import _cipher

pkg = open(r'D:/东北证券NET专业版(测试版)/cfquant_managed/<job_id>/CFQ_10110148_LITE.rzrk', 'rb').read()
src = json.loads(_cipher().decrypt(pkg).decode('utf-8', 'surrogateescape'))['content']
print('wait(0.02)' in src)   # 换成你要确认的改动
```

`<job_id>` 是托管目录名，可从 `runtime/config/qmt_strategy_jobs.json` 的 `jobs` 键读取，
或直接 `ls` 该目录。

### 一个已知的部署坑：PipeHub 接受连接失效

QMT 重启后偶现：PipeHub 进程存活、已有连接正常工作，但**无法再接受新连接**
（管道名消失，`winerror 2/3`），表现为 Web 的托管策略批准指令送不到、桥接长期卡在
`awaiting account mode confirmation`。

此时重启 PipeHub 即可恢复：

```bash
python -c "
import json,urllib.request
def api(p):
    req=urllib.request.Request('http://127.0.0.1:8765'+p,data=b'{}',
        headers={'Content-Type':'application/json'},method='POST')
    return json.loads(urllib.request.urlopen(req,timeout=60).read())
api('/api/pipe-hub/stop'); import time; time.sleep(3); print(api('/api/pipe-hub/start')['ok'])
"
```

若仍不恢复，用 `restart_cfquant.bat` 全栈重启（会一并重启 Web + PipeHub + QMT 部署流程）。

## 日志目录

本地服务日志统一写入项目根目录 `log/`：

```text
log/
  web/
    cfquant_web_server.runtime.log
    cfquant_web_server.<启动时间>.stdout.log
    cfquant_web_server.<启动时间>.stderr.log
  startup/
    cfquant_startup.log
    cfquant_web_reload.log
  lttx/
    lttx_server.stdout.log
    lttx_server.stderr.log
    YYYY-MM-DD_log.csv
    YYYY-MM-DD.log
  pipe_hub/
    cfquant_pipe_hub.stdout.log
    cfquant_pipe_hub.stderr.log
  qmt_bridge/
    cfquant_qmt_bridge.log
```

默认保留最近 30 天日志。Web 服务后台会定期自动清理，也可以在“设置 - 日志清理”中手动执行。

根目录历史遗留的 `*.log`、`log_data/`、`tx_log/` 也纳入清理和 Git 忽略。QMT `userdata/log` 清理默认关闭，需要用户在网页里显式启用。

## 运行数据目录

本地运行状态和配置数据库统一放入 `runtime/`，不提交到 Git：

```text
runtime/
  config/cfquant_web_config.json
  db/cfquant_web_config.db
  lttx/
  reports/
  media/
  cache/
  status/cfquant_pipe_hub_status.json
  screenshots/
```

旧版本根目录下的 `cfquant_web_config.db` 和 `cfquant_pipe_hub_status.json` 属于历史遗留文件，整理项目时可迁移到上述目录。

常用环境变量：

```text
CFQUANT_LOG_DIR=D:\cfquant\log
CFQUANT_LOG_RETENTION_DAYS=30
CFQUANT_LOG_CLEANUP_INTERVAL_SECONDS=21600
CFQUANT_PIPE_HUB_VERBOSE_EVENTS=0
```

`CFQUANT_PIPE_HUB_VERBOSE_EVENTS=1` 会打开 PipeHub 高频事件日志，只建议排查问题时临时使用。

## 账户缓存刷新

资产和持仓采用按需快照、回调增量更新和低频补查，不再默认启动全账号持续预热：

- 首次访问账户时查询快照；相同账户并发缓存请求会合并，避免重复查询。
- 活跃订阅默认每 30 秒补查一次完整快照，不将每条回调当作完整账户数据。
- 有明确账号、类型、桥接来源且可安全匹配的资产或单条股票持仓回调，会直接更新已有快照；缺失字段不会被填零，其他持仓不会被覆盖。
- 新持仓、无法唯一匹配的持仓以及委托、成交变化会标记相关数据待补查，同类后台补查至少间隔 2 秒。回调线程不执行 QMT 查询。
- 每项缓存订阅在 90 秒无人访问后过期。关闭网页、切到其他账号或离开资金持仓页面后，不会永久保留后台轮询；已发出的查询不会强制中断。
- 首页和交易页可见时，每 15 秒读取一次服务器缓存；这个频率不等于 QMT 查询频率。后台标签页不续订。
- 手动强制刷新、网页下单/撤单后的明确刷新、SDK 直接查询保持原有调用语义；成交和委托回调仍正常分发。

需要部署级覆盖时可设置以下环境变量，重启 Web 服务生效：

```text
CFQUANT_WEB_ACCOUNT_CACHE_INTERVAL=30
CFQUANT_WEB_ACCOUNT_CACHE_IDLE_SECONDS=90
CFQUANT_WEB_ACCOUNT_CACHE_BACKGROUND_TIMEOUT=5
```

`CFQUANT_WEB_ACCOUNT_CACHE_PREWARM_SECTIONS` 默认留空。显式设置为 `asset,positions` 可恢复所有启用账号的持续预热，预热账号不受页面空闲过期限制。已有部署设置的较短刷新间隔仍会生效。

本次调整不要求重启 QMT 策略；重启 Web 服务后刷新浏览器即可加载。未测量真实终端的下单延迟收益，离线回归见 `cfquant/tests/24_账户缓存按需刷新测试.py` 和 `cfquant/tests/25_账户缓存页面测试.py`。

## 全推订阅范围

`xtdata.subscribe_whole_quote(code_list, callback=...)` 和 Web 全推调试接口不再设置 `SH/SZ` 白名单。可以传入市场列表、证券代码列表或混合列表，包括 `BJ`；cfquant 不额外改写证券代码大小写，实际支持范围由 QMT 版本、行情权限和代码有效性决定。

普通桥的全推按请求建立独立 QMT 订阅及回调，不再复用内部沪深行情源。同一 SDK 客户端或多个客户端的订阅号相互独立；取消订阅会调用 QMT 撤销对应底层订阅。QMT 拒绝订阅时返回错误，不再仅分配本地订阅号表示成功。Web 调试页更换市场或桥接来源后会撤销旧订阅并重新订阅；Web 请求未提供市场或代码参数时，默认列表为 `SH,SZ,BJ`，显式传入的空列表不会被替换。

完整项目更新会自动同步核心包和绑定模式对应的 QMT 入口到各 QMT 目录，重启 Web 后再重启对应 QMT 策略。本次回归使用模拟 QMT，未验证券商终端的北交所行情权限与实时报价。

## QMT 日志设置

Web“设置 - QMT 日志”可以控制 QMT 侧桥接日志：

- 日志显示默认开启；
- 语言默认中文，也可以切换为 English；
- 保存后会向在线的普通桥和交易桥广播配置；
- 账号绑定写入的 `cfquant_bridge_config.json` 会保存日志语言和日志开关，QMT 入口脚本重启后继续生效。

## 版本检查

Web 左上角会显示当前版本号。鼠标悬停后可以查看：

- 当前本地版本；
- 本地更新日志；
- 远端是否存在新版本；
- 新版本更新日志；
- 版本检查失败原因。

内网或无法访问 GitHub 时，版本探测失败只会在页面顶部提示，不影响交易、行情、账号路由和本地功能。

## 更新策略

Web“设置 - 更新管理”中分为两类更新。

Web 项目更新：

- 可从 GitHub 拉取项目 zip；
- 也可以上传本地 zip；
- 更新前会生成包含受管项目源码的完整回退点，新增文件和旧文件残留也会在回滚时精确处理；默认保留最近 2 个回退点；
- 源码覆盖完成后，会在当前 Web 使用的 Python 环境中执行 `python -m pip install --editable .`，刷新已安装的 `cfquant` 包元数据；
- 页面更新结果会显示可编辑安装是否执行成功、使用的 Python 和安装后版本；
- 失败时按更新前备份恢复；
- 更新和回滚期间会暂时锁定网页新委托，已进入处理的网页交易请求会先完成后再替换文件；
- 更新后会自动调用项目根目录的 `restart_cfquant.bat`，按“停止 Web/PipeHub、等待端口释放、启动 Web”的顺序恢复服务；LTtx 按既有策略保留运行。

QMT 核心更新：

- 面向每个已绑定 QMT 的 `bin.x64/cfquant/`；
- 用于更新 QMT 侧可导入的 `cfquant` 核心包；
- 不直接替换 QMT 里的加密入口脚本。

账号初始化或保存绑定时也会复用同一套目标目录解析和备份逻辑：用户可以填写 QMT 安装目录、`bin.x64` 或相邻 `python` 目录，系统会解析到 `bin.x64/cfquant/` 并自动复制当前本地核心包。复制失败不会丢失账号配置，页面会提示具体异常，修正目录或权限后重新保存即可。

更新后的提醒：

- 完整项目更新会在覆盖核心包后提示并重新启动对应 QMT 入口。
- 完整项目更新会先关闭已绑定且正在运行的 QMT，再按绑定模式覆盖对应的 `qmt_scripts/CFQUANT*.py` 入口文件。
- QMT 入口文件由项目更新流程按绑定目录覆盖；如果目标目录不可写，更新结果会报告对应失败。

## 回滚

Web 项目更新会保留更新前备份。发生问题时可以在 Web“设置 - 更新管理”中选择备份回滚。

回滚后同样需要注意：

- Web 项目会自动调用 `restart_cfquant.bat` 重启，等待健康检查恢复；
- 回滚源码后也会重新执行 `python -m pip install --editable .`；
- 如果回滚涉及 QMT 核心包，需要重启 QMT 侧入口脚本；
- 回滚会先关闭已绑定且正在运行的 QMT，再按回滚版本覆盖对应入口文件。

交易安全边界：

- 完整项目更新会自动停止已绑定且正在运行的 QMT，再开始覆盖 Web、核心包和入口文件。
- 网页更新保护只覆盖本 Web 服务的新委托和撤单请求，不能强制停止已经运行的 QMT 策略、外部 Python 程序或其他直接连接 QMT 的交易进程；
- 如果更新过程中服务意外退出，重新启动 Web 后仍可在“更新管理”中使用已经落盘的回退点恢复。
