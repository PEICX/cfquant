# 单跳命名管道实验（NPSH_LAB / npsh_lite）

> 分支 `feature/singlehop-nopump`。目标：绕过 `cfquant_pipe_hub` 中转进程与 QMT 主线程泵，
> 外部进程**直连** QMT 内嵌 Python 的命名管道 server，查询类请求（`get_etf_iopv` 等）
> 在管道读取线程直接执行。真实 QMT 单请求目标 ≤ 30ms（AF_UNIX 同架构实验实测 26ms）。

## 架构

```
外部进程 (任意 Python 3)                QMT 终端（内嵌 Python 3.6.8）
┌──────────────────────┐               ┌─────────────────────────────────┐
│ NpshClient           │  命名管道      │ NPSH_LAB.py（模型策略）          │
│  单连接 + 常驻读取线程 │ ════════════> │  NpshServer：单实例单客户端      │
│  请求 id 关联/超时     │ \.\pipe\     │   ├ get_etf_iopv → 读取线程直执行 │
│  属性代理/事件回调     │  cfquant_    │   └ passorder  → 主线程泵执行     │
└──────────────────────┘  singlehop   │      (schedule_run 10ms 节拍)    │
                                     └─────────────────────────────────┘
```

- **单跳**：无 hub 进程、无两段管道、无 rx/tx 双连接。一条全双工管道承载请求、
  回包与 server 推送事件。
- **无 pump**：查询在 `NpshServer` 的 serve 线程内联执行（`_serve_loop → _handle →
  handler → func(*args)`），不经任何队列/定时器；只有 `passorder`（QMT 强制线程亲和）
  走 `schedule_run` 10ms 泵，与 cfquant 桥 `main_thread_queue` 同模式。
- **单客户端**：server 只创建**一个**管道实例（`max_instances=1`），第二个连接者拿到
  `ERROR_PIPE_BUSY` 直到当前客户端断开；实例断开后原句柄 `DisconnectNamedPipe` +
  重新 `ConnectNamedPipe`，客户端可随意重启。并发由 client 侧在途请求（请求 id 关联）解决。
- **与 hub 链路并存**：管道名 `\\.\pipe\cfquant_singlehop` 与 hub 的
  `\\.\pipe\cfquant_pipe_hub` 完全隔离；web/CFQUANT_LITE 不受影响，QMT 内两套并存。

### 关键实现事实：overlapped IO 是必需的

任务前提"命名管道读写天然并发"**只对 overlapped 句柄成立**。实测（`tools/probe_pipe_duplex.py`）：

- 同步句柄（无 `FILE_FLAG_OVERLAPPED`）：Windows **按句柄串行化** IO——读取线程挂起的
  `ReadFile` 会永久阻塞另一线程对同一句柄的 `WriteFile`（挂 2 秒以上不返回）。
  仓库里 hub / LTtx / PipeTxClient 全部用 rx/tx 双连接回避了这一点。
- overlapped 句柄（`FILE_FLAG_OVERLAPPED` + 每次操作独立 `OVERLAPPED` + 事件 +
  `GetOverlappedResult`）：挂起读与并发写互不阻塞（实测写 1.8ms 完成，服务端照常收到）。

因此 `npsh_lite.py` 所有句柄（server 的 `CreateNamedPipeW`、client 的 `CreateFileW`）
都带 `FILE_FLAG_OVERLAPPED`，`ReadFile/WriteFile/ConnectNamedPipe` 全部走
`_run_overlapped`。关闭时先 `CancelIoEx` 再 `CloseHandle`，挂起的 overlapped 操作以
`ERROR_OPERATION_ABORTED` 收尾，线程安全退出。

线协议（与 AF_UNIX 实验一致，仅换传输介质）：

```
frame   = "!Q"(8B 长度) + payload
payload = b"npsh1:" + 紧凑 JSON(ensure_ascii)
request  {"t":"req","id":..,"a":action,"p":[args],"k":{kwargs}}
response {"t":"res","id":..,"ok":bool,"r":result,"e":error,"c":true-if-str-coerced}
event    {"t":"evt","n":name,"d":data}        # server -> client 推送
```

client 属性代理把 `_timeout=` 作为每请求超时保留字，其余参数原样转发；
超时**不**断线（迟到回包按请求 id 安全丢弃）。

## 部署（真实 QMT）

策略名 `NPSH_LAB` 故意**不带 CFQ_ 前缀**：`CFQ_*` 是网页部署器托管命名空间
（同账号同名会被自动改写 startupAutorun），单跳实验不归它管，与 IOPV_LAB 同模式。
`build_package(name_pattern=...)` 显式放行该名字（`cfquant/qmt_strategy_package.py`）。

```bash
# 0. 校验传输块同步（改过 npsh_lite.py 先 --sync）
python tools/deploy_npsh_lab.py --check

# 1. 停止 QMT（bin.x64/XtItClient.exe 完全退出；登录卡住就杀进程等 8 秒）
# 2. 打包 + 登记（登记要求 QMT 已停止；自动备份原 XML 到 cfquant_managed/backups/）
python tools/deploy_npsh_lab.py --build    --qmt-root "D:/东北证券NET专业版(测试版)"
python tools/deploy_npsh_lab.py --register --qmt-root "D:/东北证券NET专业版(测试版)"

# 3. 启动 QMT（bin.x64/XtItClient.exe）
#    日志确认 importFormula end（python/NPSH_LAB.py 生成）+ 模型 doRun（server ready）
#    QMT 登录偶发卡住（Proxy client not logged）：杀掉 XtItClient 等 8 秒重启
python tools/deploy_npsh_lab.py --status   --qmt-root "D:/东北证券NET专业版(测试版)"
```

登记内容（`--register` 自动完成，等价于人工操作）：

- `FormulaCatalog` 下加 `<catalog scriptType="1" formulaCatalogModelType="4"
  systemProvidedStrategy="0" strategymall="0" name="NPSH_LAB" type="2" simpleRun="0"/>`
  （与 IOPV_LAB 同组）；
- `strategyTrade` 克隆 IOPV_LAB（或 CFQ_10110148_LITE）条目，改 `name=NPSH_LAB`、
  `id=现有最大+1`、`FromulaExpandData`、备注，`startupAutorun=1`；
  写回前 `minidom.parseString` 复验，原文件备份。

```bash
# 本地 mock（不依赖 QMT）：全链路自测
python qmt_scripts/npsh_lab_client.py --mock

# 自动化回归（查询直执行/passorder 线程亲和/超时/异常/并发/断线重挂/事件推送）
python -X utf8 -m pytest "cfquant/tests/34_单跳命名管道测试.py" -q

# 真实 QMT：ping + get_etf_iopv 延迟统计（验收：p50 ≤ 30ms）
python qmt_scripts/npsh_lab_client.py --stats 50

# 库用法（"外面调用和本地调用一样"）
import sys; sys.path.insert(0, "qmt_scripts")
from npsh_lite import NpshClient
qmt = NpshClient()
qmt.get_etf_iopv("510050.SH")            # 属性代理直达
qmt.get_etf_iopv("510050.SH", _timeout=1)  # 每请求超时
qmt.on_event = lambda name, data: ...    # 事件回调
qmt.passorder(code="510050.SH", op_type=23, account="10110148",
              volume=100, price=0.412)   # 真实下单，先确认参数！

# 进程清单验收：无 hub 参与（单跳）
# client → XtItClient.exe 一条管道连接（\.\pipe\cfquant_singlehop 单实例）
```

## 真机实测（2026-10-17，东北证券测试端，账户 10110148，周末空闲时段）

QMT 内同时运行 CFQ_10110148_LITE（连 hub，服务 web）、IOPV_LAB（AF_UNIX 实验）
与本策略，web/hub/LITE 全程在线：

| 阶段 | get_etf_iopv p50 | p90 | min |
| --- | --- | --- | --- |
| 初版（默认 GIL 切换间隔 5ms） | 30.7 ms | 40.6 ms | 1.1 ms |
| `sys.setswitchinterval(0.001)` 后 | **21.8 ms** | 33.1 ms | 1.8 ms |

- **p50 21.8ms ≤ 30ms 达标**（AF_UNIX 同架构参考值 26ms）。
- ping（纯传输回声）与 iopv 的 p50 几乎一致、iopv min 仅 1.8ms：瓶颈不在
  QMT 内建函数（~1ms）也不在管道，而在 QMT 内嵌 Python 的 GIL 调度——serve
  线程从 overlapped IO 唤醒后要抢回 GIL，进程内多个 10ms 泵定时器把响应量化
  成 ~10ms 台阶（LITE 注释中 500ms 量化同机制）。`init` 里调
  `sys.setswitchinterval(0.001)` 缩短切换间隔后 p50 从 ~30ms 降到 ~21ms，
  进程级生效，LITE 桥同样受益。
- 单跳拓扑：`\\.\pipe\cfquant_singlehop` 由 XtItClient 内 NPSH_LAB 创建
  （XtItClient 公式日志为证），外部 client CreateFileW 直连；hub 进程只服务
  `\\.\pipe\cfquant_pipe_hub`（web/LITE），两条管道并存互不干扰。
- **passorder 真实下单**（恒生东北 T2 仿真账户 10110148，用户确认后执行）：
  单笔 26.7ms 返回 0（已受理）；20 连发 20/20 全部受理，p50 21.5ms
  （含 serve 线程 → 队列 → 10ms 泵 → QMT 主线程真实 passorder 全程）。

## 已知边界

- server 串行处理请求：查询直接在 serve 线程执行，一个慢查询会排队后续请求
  （单客户端实验语义；并发在途请求仍是并发的，只是 server 侧按到达序执行）。
- `passorder` 在 serve 线程上等待泵执行（最长 10s），期间该连接的后续请求排队。
- 事件推送接口（`send_event` / `on_event`）已在传输层与测试覆盖；lab 白名单暂未
  挂 QMT 回调源，需要时在 NPSH_LAB 里加动作/回调即可。
- 管道无 ACL（与 hub 一致），本机任意进程可连；实验环境可接受。
